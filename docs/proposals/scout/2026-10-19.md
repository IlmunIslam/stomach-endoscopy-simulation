## Proposal 1: Claude Code PreToolUse hook guarding execute_blender_code (adopt)

- What it is (F): a Claude Code hook that runs a small script before every tool call. MCP tools appear as `mcp__<server>__<tool>`, so the matcher `mcp__blender__execute_blender_code` selects it. The script reads JSON from stdin (`tool_name`, `tool_input`), and exit code 2 blocks the call and sends stderr to Claude as the reason. [high] https://code.claude.com/docs/en/hooks
- Bottleneck: safer Blender work. CLAUDE.md rule 1 (never save) and LESSONS 2026-10-15 (File > Revert used twice on the working .blend) are currently enforced only by instructions. A hook enforces them mechanically.
- Evidence it works: the docs give this exact pattern (block by inspecting `tool_input`). I found no case study of it on Blender MCP specifically. [medium]
- Caveats (F): a crashed or timed-out hook lets the call through by default; `"onFailure": "block"` fixes that but needs Claude Code v2.1.295 or later (verify your version with `claude --version`). A wrong script path fails silently non-blocking, so test it first. The `tool_input` key name for the code string is unverified; print one real call's input to a log and read it before relying on the regex. [medium]
- Licence: none, it is your own ~15-line script. Commercial use not an issue.
- Last commit/maintenance: n/a (built-in Claude Code feature).
- Security: runs locally with your user rights; no network. Keep the script in the repo, review it, call it with `python -I`. Pin nothing external. It reads tool input only. A string match is bypassable by obfuscated code (for example building the operator name from pieces), so it is a seatbelt, not a sandbox. (O)
- Fit: Windows OK (use a Python script, not jq/bash, since jq is not guaranteed on Windows). Zero RAM/GPU cost. Claude Code Pro supports hooks.
- Effort: about 20 minutes.
- Block list to start: `save_mainfile`, `save_as_mainfile`, `wm.revert_mainfile`, `open_mainfile`, `wm.read_homefile`, `wm.quit_blender`, `bpy.ops.wm.save`, `wm.recover`. Allow `save_as_mainfile(..., copy=True)` only if you want to; simplest is to block it too and ask.
- 3-step test plan (on a copy of the project, scene untouched):
  1. Add the hook to a scratch `.claude/settings.local.json` (not the shared settings); script logs `tool_input` to a text file and exits 0. Run one harmless `execute_blender_code` (`return 1+1`) and read the log for the real key name.
  2. Switch the script to block on a regex of the list above. Ask Claude to run code containing `bpy.ops.wm.save_mainfile` inside a string comment on a scratch .blend copy; confirm the block message appears and the file timestamp is unchanged.
  3. Confirm a normal read-only call still passes, then test the failure case (rename the script) and watch for the hook error notice.
- Expected gain: removes the repeat failure class "agent saved/reverted the working file" (LESSONS high-severity). Minutes saved: avoids a lost-file recovery, which cost a whole attempt on 2026-10-15.
- Verdict: adopt (needs the user's own settings change; I did not touch any config).

## Proposal 2: Blender 5.2 LTS with the Cycles texture cache (try, on a copy)

- What it is (F): Blender 5.2 LTS, released 2026-07-14, supported until July 2028. Cycles gets a texture cache that creates a `.tx` file per image (stored in a `blender_tx/` folder), loads only needed tiles and mip levels, and evicts unused images; Simplify gains a Texture Resolution setting (e.g. 50% or 25%); geometry memory is also reduced by sharing some memory with Blender. [high] https://developer.blender.org/docs/release_notes/5.2/cycles/ , https://code.blender.org/?p=13206 , https://developer.blender.org/docs/release_notes/5.2/
- Bottleneck: render speed and memory on 8 GB RAM. The scene has 300k-vert meshes and several 4K-class PBR maps (Color, NormalGL, ORM per part).
- Evidence it works: developers say memory stays roughly flat as resolution grows on 4K-16K tiled renders; smaller tiles (512 or 1024) cut memory further at some speed cost. [medium; dev blog claim] I found NO benchmark on 8 GB hardware, and the savings depend on texture vs geometry share. Your scene is geometry-heavy, so the gain may be small. [high that no benchmark was found]
- Downsides (F): small render-speed cost, extra disk use for `.tx` files; compatibility notes: Geometry Nodes asset files with tools must be re-saved in 5.2, Compare and Random Value node socket identifiers changed, and the Python API for accessing Geometry Nodes modifier properties changed. Your scene uses GN time gates (LESSONS 2026-10-18), so the API change could break `tools/` scripts. [medium, from release notes index] OIDN is not GPU accelerated on RDNA2 AMD (irrelevant for your NVIDIA MX450). NVIDIA OptiX minimum driver is 575 (the MX450 cannot use OptiX anyway, it is CUDA-only if at all; I could not confirm 5.2 CUDA support for this GPU, so I could not find this). [low]
- Licence: GPL; commercial use allowed for output and use.
- Last commit/maintenance: LTS, maintained to July 2028.
- Security: official signed installer from blender.org; no new network behaviour known. Install side by side (5.1 and 5.0 already coexist). The Blender MCP add-on must be separately installed per version, so pin its commit before enabling it in 5.2 (see INDEX: Blender Lab MCP).
- Fit: Windows OK. Unverified for MX450 2 GB; you render on CPU anyway.
- Effort: about 45 minutes (install, open copy, re-test scripts).
- 3-step test plan:
  1. Install 5.2 LTS alongside 5.1; open a COPY of the .blend in 5.2 from the command line (`blender.exe -b copy.blend --python render_one.py`, frame 361) and never save over the original.
  2. Render frames 361/531/731/971 with texture cache off then on (and Simplify texture resolution 50%); record peak RAM in Task Manager and render time; compare images with tools/render_stats.py.
  3. Run the repo's tools scripts that touch GN modifiers on the copy to find API breaks.
- Expected gain: uncertain; maybe lower peak RAM during rendering if textures dominate. Real gain only known after step 2. Also gets you on a supported LTS. (O)
- Verdict: try (low priority, on a copy). Do not migrate the working file mid-task.
